Soft Robotics for an Adaptive Space Exercise Harnessing System

Astronauts spend upwards of 10 hours exercising each week and still experience significant muscle atrophy and bone density loss. This project focused on developing a soft robotic harness system that can adaptively control loading using sensor feedback and machine learning, with the goal of improving exercise effectiveness in microgravity. As the only electrical team member, I designed and integrated a highspeed, portable pneumatic system and developed a machine learning model to control harness loading in real time.

Undergraduate Researcher
texlab @ Rice University

Brainstorming

Current exercise harnesses and astronaut exosuits lack the adaptability needed for effective muscle and bone health maintenance in microgravity environments. To address this, our team proposed a novel soft robotic harness system that integrates pneumatic artificial muscles (PAMs) with real-time sensor feedback. The PAMs provide lightweight, natural compliance, and the embedded sensors monitor loading.

I took the lead on the electrical side of the project, focusing on data collection, a pneumatic regulation system, and adaptive control to accomodate user variation and actuator hysteresis. I also collaborated closely with the mechanical team to ensure seamless integration of sensors and actuators.

Interestingly, I joined the Space Wearables team at texlab mid-semeter, when most of the lit review and technical workshops had been completed. This meant learning to build the knit pneumatic actuators and catch up on reading in a fraction of the time while simultaneously managing the hardware and software integration.

Sensor Selection and Calibration

When considering our sensing suite, we knew that loading would vary across the harness, so I proposed a multi-sensor approach that integrated force sensitive resistors (FSRs) with s-type strain-gauge load cells. The FSRs would be embedded in the shoulder straps to capture localized pressure distribution, while the load cells would be mounted inline with the pneumatic actuators to measure the overall tension.

To verify that this approach could reliably judge harness loading, I calibrated the sensors and simulated strap forces to observe potential drift and non-linearity. The calibration process revealed that the load cells provided stable, linear readings, but the FSRs exhibited significant drift.

Additionally, our load cell amplifier is designed to be a USB Native Peripheral Device, which I soon realized would be a bottleneck for our real-time control loop. Because MATLAB operates on a single-thread by default, polling the load cell over the USB bus disrupts the timing of the Arduino's serial communication. So rather than attempting to handle multiple asynchronous hardware protocols, I developed a python script to facilitate hardware communication between MATLAB and the Arduino serial port while using the Phidget22 library to read the load cell voltages.

Pneumatic System

Before I joined the team, previous iterations of the harness focused primarily on sensing and comfort, relying on a wall air compressor for inflation. My role was to transition the project toward "dynamic adjustability" by developing a lightweight and portable air control system. To achieve this, I designed a digital system powered by an Arduino Uno microcontroller. The architecture regulates a micro-vacuum pump and 4/2 solenoid valve using logic-level MOSFET switching circuits. By adjusting the pump's duty cycle and toggling the valve state to switch the actuator port connections, the system achieves precise inflation and active deflation.

During testing, I found that decreasing the sampling interval caused the pump to experience sudden, aggressive jolts. I deduced that rapid pump switching was causing magnetic pushback, which interferred with the pressure sensor power and caused the control loops to overreact. To safely gather training data, I established a baseline sampling rate of 0.2 Hz during initial testing.

Pneumatic Control and ML Model

Standard linear control models like PID fail when managing pneumatic artificial muscles. Because PAMs are constructed from knit sleeves, they exhibit hysteresis: the pressure required to contract the muscle during inflation is completely different from the pressure measured at that exact same length during deflation. If you push the PID gains high enough to overcome this internal friction, the system immediately overshoots and oscillates.

To solve this, I designed an Adaptive Neuro-Fuzzy Inference System (ANFIS) to act as a feedforward component in the control loop. I selected 4 specific inputs for the model to map the system's states:

  • Current Pressure: Tracks our position on the loading/unloading cycle.
  • External Load: Accounts for user compliance and variable body shapes.
  • Force Error: Acts as our primary input signal (Setpoint - Sensor Reading).
  • Change in Force Error: Evaluates how fast we approach the target to prevent overshoot.

Crucially, the sign of this error tells the model which side of the hysteresis loop we are currently on to establish a clean one-to-one mapping for inverse modeling. Put simply, the fuzzification layer utilizes Gaussian membership functions to calculate membership grades for each input, which are then multiplied in the product layer to determine their "firing strength". In the defuzzification stage, a Sugeno rule architecture outputs a weighted average. This output is our control signal, which is fed into the Arduino to drive the pump and valve. The sign will determine the solenoid state, and the magnitude will determine the duty cycle of the pump PWM signal.

Data Collection

Collecting the training data for our model meant implementing a simple PID controller to achieve certain target pressures. The tunning process made it painfully obvious that standard PID control was unfit for our system. The Simulink PID autotuner struggled to converge because of the actuator nonlinearity, so I manually tuned the parameters. I started by increasing the proportional gain until the system could reach the target pressure with minimal overshoot. The integral gains were then slowly increased to achieve a faster response while maintaining accuracy.

Once the actuator could reach the target pressure within an acceptable tolerance, I worked with the team to design a testing rig and subjected the actuators to a 0.05 Hz sinusoidal reference signal varying between 3.447 kPa and 17.24 kPa (0.5 to 2.5 PSI) across three cycles. In each cycle, I applied variable external loads between 0.5 kg and 2 kg. The MATLAB Simulink ANFIS model utilizes a hybrid learning algorithm combining backpropagation gradient descent and least-squares estimation. A major theoretical hurdle was defining the "target force" during training data collection. I evaluated multiple strategies:

  • Force-controlled PID: Allowing a step signal to drive the pump directly via force error.
  • FSR vs. Load Cell Comparison: Using pressure control but evaluating the delta between the FSR and the load cell.
  • Stable Step Response Mapping: Waiting for the pressure to stabilize at various PSI steps and mapping the final achieved force.

Ultimately, I chose to use the FSR readings as the reference force. This meant that the model would be learning to predict the control signal based on the FSR readings rather than the actual load cell force. However, it was the only way to ensure that the training data was consistent enough for the model to learn effectively and capture the transient dynamics.

Final Integration and Results

Finally, I soldered the components together. This was exceptionally difficult, but the result was a compact pneumatic control board. Next, I extracted the optimized premise and consequent parameters from the trained model and converted them into fixed-point lookup matrices directly inside the Arduino firmware.

By pairing the ANFIS feedforward output with a conservative feedback loop, the system effectively mitigated the soft robotic hysteresis. The hybrid control architecture minimized overshoot and successfully adapted the harness across different shoulder configurations.

Reflections

In future iterations, I hope to migrate the ANFIS forward pass to an ESP32 to handle the mathematical processing, and low-level sensor aggregation. My primary focus will also be implementing deadband testing to map the minimum voltage for pump movement, and resolving the pump jolts by isolating electromagnetic feedback and optimizing initial PID gains.

This project put me in the unique position of being the only electrical engineer on a team of mechanical engineers. Furthermore, joining mid semester meant overcoming a steep learning curve. It taught me how to quickly grasp and apply new technical skills. Most importantly, I practiced communicating my ideas effectively to a team with a completely different background. I also learned how to navigate ambiguity and make informed decisions with incomplete information. The experience taught me lessons I’ll carry forward throughout my career.

Multithreaded ROS 2 Navigation Architecture for Autonomous Vehicles in C++

The objective of this project was to design and deploy a modular, production-grade autonomous navigation software architecture for a TurtleBot3 mobile robot. Built entirely using Modern C++ (rclcpp) within the ROS 2 (Robot Operating System) middleware layer, the system enables a differential-drive robot to autonomously localize, safely follow winding corridors, and dynamically log its path state machine. The overarching framework splits core functionality into reactive behavioral logic (Topics) , synchronous structural setup routines (Services) , and long-running asynchronous tracking tasks (Actions) , validating it first in a Gazebo physics simulation environment before deploying onto physical robotic hardware.

Developer
C++ · ROS2

Reactive Wall-Following Behavior via Custom Topic Nodes

The Goal: Build a responsive node that subscribes to raw /scan data (LaserScan) and publishes steering geometry to /cmd_vel (Twist) to dynamically regulate the robot at a stable 30cm clearance from a right-hand wall.

The Challenge & Structural Struggle: During the initial testing phases of this bang-bang controller, the robot exhibited severe edge cases. Setting the safety threshold for oncoming walls to 0.3 meters resulted in collisions, as processing latencies and the robot's physical inertia caused it to impact the wall before the angular turn could execute. Conversely, widening the safety gap to 0.4 meters introduced an insidious bug: if the robot drifted or pitched slightly into the wall on a straightaway, the single-ray front laser would clip the side wall at an angle, misidentifying a normal corridor as an impending wall and triggering a corner-cut midway through a straight trajectory.The Architectural Fix: To resolve this, I transitioned from scanning a single, brittle 1D laser array index (msg->ranges[0]) to an adaptive forward-arc sampling window. This filter captured the true geometric minimum distance ahead, neutralizing false positives from minor body weaving. Additionally, I decoupled speed from the steering behavior; when the forward laser window drops below 0.5 meters, the linear tracking speed is drastically choked down from 0.15 m/s to a crawl of 0.03 m/s. This manipulation of linear kinetic momentum allowed the system's aggressive 0.35 rad/s angular turning velocity to cleanly rotate the chassis clear of corners without any threat of physical collisions.

Synchronous Initialization via Custom Service Server

The Goal: Create a synchronous find_wall Service Server (FindWall.srv) that acts as a pre-flight initialization routine. When called, the robot must programmatically find the nearest obstruction, drive straight up to it, flush its alignment parallel to the surface, and return a clean execution state (wallfound = true) before releasing control back to the core tracking loop.

The Challenge & Structural Struggle: Implementing a multi-phase linear and angular movement routine strictly inside a standard ROS 2 callback block completely froze the node's single-threaded executor stack. Because the service handler took several seconds to complete its spatial searches and wall alignments, it starved the incoming /scan subscriber thread of execution time. Without sensor updates flowing, the node could not read changing laser arrays, causing the robot to lock up or spin indefinitely. The Architectural Fix: This problem required a deeper dive into the ROS 2 concurrency model. I refactored the underlying node to utilize a MultiThreadedExecutor and explicitly bound the service server callback to a isolated ReentrantCallbackGroup. This architecture separated the long-running service execution pipeline from the sensor ingestion pipeline. By allowing the executor to spawn concurrent worker threads, the service client could safely block and command velocities while the secondary callback thread continuously refreshed the internal variables with high-frequency LiDAR scans, creating an atomic, failsafe alignment sequence.

Asynchronous State Estimation via Custom Action Infrastructure

The Goal: Implement a long-running, non-blocking Action Server (OdomRecord.action) named record_odom. The action client must invoke this server to continuously track, compute, and buffer the robot's spatial $(x, y, \theta)$ odometry frames every second, outputting live mileage feedback and terminating with a definitive vector list of points upon completing a full navigation circuit.

The Challenge & Structural Struggle: Managing the life cycle of an action client concurrently alongside an operational wall-following timer loop introduced complex thread-synchronization problems. The main challenge was maintaining a completely unblocked, highly deterministic 10Hz operational wall timer loop while simultaneously processing non-blocking asynchronous future objects (async_send_goal) returned from the action client initialization. If the action feedback callbacks or result states were handled on the wrong execution timeline, it created race conditions that caused sudden, erratic movements or prematurely issued stop commands (stop_msg) before the robot completed its lap. The Architectural Fix: I addressed this by structuring a clean, event-driven state machine using std::bind to hook explicit, isolated callback routines for goal responses, live feedback loops, and final wrapped results. Operational wall-following code remains completely gated behind an atomic boolean flag (wall_follow_ready_), which is strictly flipped to true only when the service confirms alignment and the asynchronous action server safely returns a validated goal handle. When the action server finally reports a SUCCEEDED status code indicating circuit completion, the result thread cleanly intercepts execution, flips the operational flag to false, overrides the timer velocities, and publishes an explicit zero-velocity vector to gracefully park the platform. This highlights my ability to implement safe, decoupled, multi-threaded robotics software.

Results & Learnings

The successful implementation of this navigation stack demonstrated the viability of using decentralized, asynchronous architectures for real-time edge computing on autonomous mobile robots. By debugging complex multithreading issues, dealing with physical inertia gaps in physics simulation, and mastering the ROS 2 computational graph, I advanced from writing standalone scripts to constructing coordinated, industrial-grade robot software frameworks. Moving forward into my career, this project serves as foundational proof of my ability to build deterministic systems that successfully bridge the gap between high-level hardware-agnostic logic and real-world raw sensor inputs. The exact paradigms I mastered here—such as breaking away from blocking processes via ReentrantCallbackGroups, managing thread pools with explicit executors, and configuring asynchronous feedback states—are the core competencies required to scale enterprise-level autonomous mobile robots (AMRs), self-driving vehicles, and complex factory automation cells. This experience fundamentally elevates my engineering profile from a hobbyist to a production-capable robotics software developer.
